# قدرات — خطة بناء منصة متكاملة

> وثيقة عمل. الإصدار 2، ٤ أكتوبر ٢٠٢٦. تُحدَّث مع كل مرحلة منجزة.
> القرارات المعلّقة موسومة **[قرار مطلوب]**.

## نطاق المنتج (محدَّد)

**المنصة للطلاب فقط، والاشتراك مقابل محاكاة اختبار قياس.** لا لوحات معلّمين، ولا حسابات
مؤسسات، ولا إدارة فصول. كل ميزة تُقاس بسؤال واحد: هل تجعل الطالب أقدر في المحاكاة؟

ما يترتّب على هذا:

- **أُسقط مسار B2B بالكامل.** كانت توصيتي أن يأتي أولًا؛ القرار خلافه، والخطة تتبع القرار.
- **المعايرة أبطأ.** عقد مدرسة كان سيأتي بـ٦٠–٣٠٠ طالب دفعة واحدة. بالطلاب الأفراد يصل
  البنك إلى ٣٠٠ إجابة لكل سؤال بعد شهور، لا أسابيع. لذا: **افتح طبقة مجانية سخيّة في
  التدريب** — كل إجابة مجانية تعاير البنك، والمعايرة هي الأصل الدفاعي.
- **الاحتفاظ هو المقياس الحاكم**، لا عدد المقاعد. طالب واحد يتسرّب = إيراد مفقود كاملًا،
  بلا عقد سنوي يمتصّ التقلّب.
- **الموسمية غير مكبوحة.** الطلب يتضخّم قبل موعد الاختبار وينهار بعده، ولا عقود سنوية
  تسوّيه. السعر والتسويق يجب أن يُبنيا على هذا، لا أن يفاجأا به.

## ١. تقييم الواقع الحالي

### ما هو جاهز فعلًا ويستحق البناء عليه

| المكوّن | الحالة |
|---|---|
| بنك الأسئلة | ١٤٩٠ سؤالًا، مراجَعة تحريريًا بالكامل (١٠ دفعات موثّقة في `audit-batch-*.html`) |
| محاكاة قياس | `dist/qiyas.js` — ١٢٠ سؤالًا، ٥ أقسام × ٢٤ سؤالًا × ٢٥ دقيقة، أوزان النوعين لكل مسار، منع الرجوع للقسم المغلق |
| موثوقية الجلسة | `dist/engine.js` — استئناف، حفظ الوقت المرصود/غير المرصود، انتهاء المهلة، حماية التبويبات المتزامنة |
| المصادقة | `scrypt` (N=16384) + salt، `timingSafeEqual`، hash للجلسة في القاعدة، كوكي `HttpOnly; SameSite=Lax; Secure` |
| الاختبارات | ٥ مجموعات، ٦ تأكيدات PASS، تمر كلها بلا تبعيات خارجية |
| النشر | `Dockerfile`، `DEPLOY.md`، صفر تبعيات npm (يعتمد `node:sqlite`) |

هذا أساس أقوى من معظم ما يُسمّى "منصة" في هذا السوق. المشكلة ليست في الجودة، بل في **السقف**.

### العوائق الخمسة الحقيقية أمام التوسع

**١. التقدّم مخزَّن ككتلة JSON واحدة — وهذا يمنع كل شيء تجاري**

```sql
CREATE TABLE progress (
  user_id INTEGER PRIMARY KEY,
  data    TEXT NOT NULL,   -- ← كل تاريخ الطالب في نص واحد
  rev     INTEGER NOT NULL
)
```

الخادم ليس قاعدة بيانات تعليمية، بل **خزانة مزامنة**. لا يوجد صف واحد لكل إجابة. النتيجة المباشرة: لا تقارير للمعلّم، ولا معايرة للأسئلة، ولا محرّك تكيّفي، ولا لوحة مؤسسة، ولا تحليل تسرّب، ولا أي مقياس منتج. أي ميزة تجارية تمرّ من هنا. **هذا هو عنق الزجاجة الأول والوحيد الذي يستحق لقب "حاسم".**

**٢. تصنيف المهارات منهار إحصائيًا**

٦٣١ قيمة `skill` مختلفة على ١٤٩٠ سؤالًا = **٢٫٤ سؤال لكل مهارة**. لا يمكن قياس إتقان مهارة بسؤالين، ولا بناء تشخيص عليها، ولا تخصيص تدريب. التصنيف الحالي وصفٌ تحريري لا أداة قياس.

**٣. توزيع الصعوبة مقلوب، والصعوبة نفسها تخمين**

| | سهل | متوسط | صعب |
|---|---|---|---|
| لفظي | ٤٨٤ | ١٥٦ | ٦٠ |
| كمي | ٤٦٢ | ٢٤١ | ٨٧ |
| **المجموع** | **٩٤٦ (٦٣٪)** | **٣٩٧ (٢٦٪)** | **١٤٧ (٩٪)** |

اختبار قياس يفرّق بين الطلاب في الأعلى، والمنصة أفقر ما تكون هناك. و`difficulty` حقل نصي يدوي — الواجهة نفسها تعترف: «الصعوبة تقدير تحريري يحتاج معايرة بنتائج الطلاب». بلا معايرة تجريبية لا معنى لـ«مستواك» ولا لأي توقّع درجة.

**٤. النصوص مكرّرة بلا كيان مستقل**

٢٥٤ سؤال استيعاب مقروء، والنص مكتوب **داخل** كل سؤال — حتى ٥ نسخ لنفس النص. تعديل نص واحد = ٥ تعديلات. والطالب يرى النص يُعاد من الصفر مع كل سؤال، بينما قياس يعرض نصًا واحدًا وتحته أسئلته.

**٥. الشفرة مكتوبة بأسطر فائقة الطول**

`dist/core.js` = ١٤ سطرًا في ٨ كيلوبايت. `data.js` سطر واحد في ١٤٠٠ كيلوبايت. يعمل، لكنه يجعل المراجعة والعمل الجماعي وتتبّع الأخطاء في git مكلفًا. ولا يوجد `.github/workflows` — **لا تكامل مستمر على الإطلاق**: الاختبارات الخمس الجيدة لا تُشغَّل تلقائيًا على أي تغيير.

### فجوات الأمان المتبقية

**تصحيح لتقييم أول:** قلتُ في الإصدار 1 إنه «لا يوجد تحديد لمعدّل محاولات الدخول» و«لا
تدوير لرمز الجلسة». **الأمران غير صحيحين.** القراءة الدقيقة للشفرة:

- `limiter(20, 15 * 60 * 1000)` موجود على الدخول، و`limiter(10, 60 * 60 * 1000)` على التسجيل.
- الدخول يُصدر رمزًا عشوائيًا جديدًا دائمًا ويتجاهل أي كوكي واردة، فتثبيت الجلسة ممنوع أصلًا.
  وتغيير كلمة المرور يحذف كل جلسات المستخدم ثم يُصدر واحدة جديدة.

الفجوات الحقيقية بعد التحقّق:

| الفجوة | الخطورة | الحالة |
|---|---|---|
| حدّ الدخول بـ IP وحده | **عالية** — حساب واحد يُقصف من عناوين كثيرة، ومدرسة كاملة خلف عنوان واحد تُحبس | ✅ المرحلة ٠ |
| كلمة مرور مؤقتة `randomBytes(6)` = ٤٨ بتًا | متوسطة | ✅ المرحلة ٠ |
| لا سجل تدقيق لأفعال المدير | متوسطة — التصفير والتعطيل بلا أثر | ✅ المرحلة ٠ |
| لا تحقّق من البريد | متوسطة — حسابات وهمية، ولا استرجاع ذاتي | المرحلة ١ |
| الصلاحيات من `ADMIN_EMAILS` فقط | **منخفضة** بعد حصر النطاق على الطلاب — لا حاجة لأدوار معلّم | مؤجَّل |
| الحدّ في الذاكرة ويضيع بإعادة التشغيل | منخفضة — لا يستطيع المهاجم إعادة تشغيل الخادم | مقبول |

## ٢. القرار المعماري الحاسم

**قبل أي ميزة: تحويل `progress` من كتلة إلى أحداث.**

```sql
-- الجدول الذي يفتح كل شيء
CREATE TABLE responses (
  id           INTEGER PRIMARY KEY,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  item_id      TEXT    NOT NULL,
  session_id   TEXT    NOT NULL,   -- تدريب / تشخيص / محاكاة
  mode         TEXT    NOT NULL,
  chosen       INTEGER,            -- NULL = تُرك فارغًا
  correct      INTEGER NOT NULL,
  ms_spent     INTEGER NOT NULL,
  seq          INTEGER NOT NULL,   -- ترتيب السؤال في الجلسة (لقياس الإجهاد)
  answered_at  TEXT    NOT NULL,
  client_rev   INTEGER NOT NULL    -- للمزامنة وكشف التكرار
);
CREATE INDEX responses_user_time ON responses(user_id, answered_at);
CREATE INDEX responses_item      ON responses(item_id);
```

صفٌّ واحد لكل إجابة. منه تُشتق — بلا أي تغيير آخر — معايرة الأسئلة، وتقارير المعلّم، ونماذج الإتقان، ومقاييس النشاط، والتوصية التكيّفية.

**الاحتفاظ بالمزامنة بالكتلة بالتوازي** في أول مرحلة: الواجهة الحالية تعتمد عليها، و`test-server.cjs` يغطيها (مزامنة جهازين مع كشف التعارض). الكتلة تصبح لقطة مشتقّة، لا مصدر حقيقة. تُسحَب بعد انتقال الواجهة.

**[قرار مطلوب] SQLite أم Postgres؟**
SQLite + `node:sqlite` كافٍ حتى ~٥٠٠٠ مستخدم نشط على خادم واحد، بصفر تبعيات — وهذه ميزة حقيقية. وبعد إسقاط مسار المؤسسات لم يبقَ من يطلب تعدّد الخوادم. توصيتي: **ابقَ على SQLite**، وراجع القرار فقط عند تجاوز ~٥٠٠٠ مستخدم نشط أو عند الحاجة لنسخ احتياطي حيّ، واكتب طبقة الوصول في `server/db.js` بحيث لا تنتشر عبارات SQL في `server.js` — فتصبح الهجرة لاحقًا تغييرًا في ملف واحد لا إعادة كتابة.

## ٣. المراحل

كل مرحلة لها **معيار إنجاز قابل للتحقق**، لا "تم العمل عليها".

### المرحلة ٠ — سياج الأمان ✅ **منجزة**

| ما نُفِّذ | الموضع |
|---|---|
| جدول `responses`: صف لكل إجابة، مع `chosen` و`status` و`exam_id` | `server/db.js` |
| استيعاب من لقطة العمل عند كل حفظ، **بلا أي تغيير في واجهة المزامنة** | `ingest()` في `server.js` |
| تسجيل الخيار المختار في سجل الإجابات (تحليل المموّهات) | `dist/engine.js`، `dist/app.js` |
| حدّ دخول **لكل حساب** بجانب حدّ العنوان (٨ / ١٥ دقيقة) | `loginEmailLimit` |
| سجل تدقيق `admin_audit` لكل فعل إداري ناجح | `audit()` |
| كلمة المرور المؤقتة من ٦ بايت إلى ١٢ (٤٨ → ٩٦ بتًا) | `/api/admin/student` |
| CI: `npm test` على Node 22 و24، + التحقّق أن `data.js` مولَّد من `data.json` | `.github/workflows/ci.yml` |
| مجموعة اختبار سابعة تغطّي كل ما سبق | `scripts/test-analytics.cjs` |

**قرار تصميمي:** الاستيعاب **مشتق** من الكتلة على الخادم، لا من واجهة برمجية جديدة. الربح:
صفر تغيير في الواجهة، صفر خطر على الحفظ، و**تعبئة رجعية** — تاريخ كل طالب قديم يتحوّل
صفوفًا عند أول حفظ له. الكتلة تبقى مصدر الحقيقة حتى تنتقل الواجهة في المرحلة ٢.

**مؤجَّل بقرار صريح:**

- **`ms_spent`** — لا مصدر دقيق لزمن السؤال في الواجهة الحالية. استنتاجه من الفارق بين
  إجابتين يخلط زمن التفكير بزمن الانقطاع، وبيانات توقيت مضلّلة أسوأ من غيابها لأن المرحلة ٢
  تبني عليها تمييز «لا يعرف» من «يعرف ولا يُنجز». العمود موجود وجاهز؛ يُملأ عند لمس واجهة
  التدريب في المرحلة ١.
- **تقسيم ملفات الواجهة فائقة الطول** — كان بندًا في الإصدار 1. تبيّن أن ملفات الخادم
  (٥٢ حرفًا للسطر وسطيًا) سليمة أصلًا، والكثافة محصورة في `dist/*.js` التي ستُعاد كتابتها
  في المرحلتين ١ و٢. إعادة تنسيقها الآن = diff ضخم بلا ربح وظيفي، ثم تعارضات دمج لاحقًا.

**معيار الإنجاز المتحقّق:** ٧ مجموعات اختبار تمر، لا تأكيد واحد في الاختبارات الستة السابقة
عُدِّل، وملف CI يشغّلها على نسختي Node.

### المرحلة ١ — المحتوى والقياس (٣–٤ أسابيع)

**٠. بوابة إدخال الأسئلة ✅ منجزة**

مدخلان، ومُصادِق واحد: `server/items.js`. كل مسار يمرّ منه، ولا يوجد طريق يتخطّاه.

| المسار | الواجهة | الحالة |
|---|---|---|
| يدوي | نموذج في `dist/items.html` | ✅ |
| رفع Excel | القالب المرفق نفسه، يُقرأ في المتصفح ويُرسل كصفوف | ✅ |
| مؤلَّف آليًا | نفس المسارين، مع تسجيل اسم النموذج إلزاميًا | ✅ |

الضوابط المُنفَّذة:

- **حرس التكرار** — بصمة من النص المعيَّر + مجموعة الخيارات مرتّبة. إعادة كتابة السؤال
  بهمزات مختلفة أو أرقام عربية/لاتينية أو ترقيم زائد أو ترتيب خيارات مختلف **لا تمرّ**.
- **`draft → reviewed → live`** — والنشر يعيد التحقّق كاملًا: الشرح والمرجع مطلوبان قبل
  النشر لا قبل الحفظ، فالمسوّدة الناقصة لا تصل للطالب.
- **السؤال المولّد آليًا لا يُنشر قبل مراجعة بشرية موثّقة** — بحرسين: آلة الحالات تمنع
  `draft → live`، وفحص صريح يرفض النشر إن لم يكن هناك `reviewed_at` مسجَّل. الحرس الثاني
  موجود كي لا يسقط الضمان لو عُدِّل جدول الانتقالات لاحقًا.
- **تعديل سؤال منشور يُرجعه للمراجعة** — الطلاب يقرؤونه الآن.
- **رفض جزئي** — ملف من ٢٠٠ سؤال فيه صف خاطئ يُضيف ١٩٩ ويخبرك بالصف ورقمه كما في Excel.
- **سجل مراجعات** `item_revisions` لكل إنشاء وتعديل ونقل حالة، بالقيمة قبل وبعد.

**اختبار بمتصفح حقيقي** (`scripts/test-items-browser.cjs`): القالب المرفق الفعلي يُقرأ
ويُستورد، وإعادة رفعه تُرفض كتكرار، والنموذج يفرض تسمية الأداة، والقائمة تنشر عبر المراجعة.

**٠.٥ هجرة البنك ✅ منجزة**

`node server/cli.js migrate-bank` ينقل البنك من `dist/data.json` إلى جدول `items`:
**١٤٨٩ سؤالًا بحالة `live`** مع سجل المراجعة التحريرية وبصمة كل سؤال. آمن للتكرار،
والدفعة في معاملة واحدة (مُختبَر بحقن فشل بعد ١٠ إدخالات: القاعدة ترجع فارغة).

**ما كشفته الهجرة — والأهم أنها كشفت عيبًا في شفرتي لا في البنك:**

المُطبِّع الذي كتبته لحرس التكرار كان يستخدم قائمة سماح (`\p{L}\p{N}` فقط)، فكان **يحذف
الإشارات الرياضية**. النتيجة: ١٥ سؤالًا سليمًا بدت «خياراتها متكررة»:

| ما في البنك | ما رآه المُطبِّع |
|---|---|
| `["7","-7","0","14"]` | `"7","7","0","14"` |
| `["س > 5","س < 5",…]` | `"س 5","س 5",…` |
| `["(س + 8)(س − 3)","(س − 8)(س + 3)"]` | `"س 8 س 3"` للاثنين |

هذا كان سيمنع ١٥ سؤالًا من الهجرة، **وسيرفض مستقبلًا أي سؤال كمي يختلف عن آخر بالإشارة
فقط** — وهو الشكل الطبيعي لمجموعة خيارات كمية. أُعيد كتابة المُطبِّع بقائمة منع: يحذف ترقيم
الجملة ويُبقي كل عامل رياضي، ويحمي الفاصلة العشرية، ويوحّد `×`/`*` و`÷`/`/` وأشكال السالب،
ويتجاهل المسافات حول العوامل (`س - 7` = `س-7`) وبين الرقم وما يليه (`3س` = `3 س`).
٢١ حالة اختبار تحرس الاتجاهين.

بعد الإصلاح: **٠ سؤال يفشل التحقق، ٠ يفشل الصارم، وتكرار حقيقي واحد**:

`Q-G-044` و`Q-C-005` سؤال واحد بنفس الإجابة، يختلفان في الترقيم وترتيب الخيارات
و**التصنيف** (الجبر مقابل المقارنة الكمية). الهجرة تُبقي الأول وتذكر المعرفَين — القرار
تحريري لا آلي. **توصيتي:** `المقارنة الكمية` هو التصنيف الصحيح (السؤال مقارنة كمية فعلًا)،
لكن شرح `Q-G-044` أوفى. انقل الشرح الأوفى إلى التصنيف الصحيح واحذف الآخر.

**ما لم يتغيّر:** الواجهة ما زالت تقرأ `dist/data.js`. الجدول الآن مصدر موازٍ مكتمل؛ تحويل
الواجهة لتقرأ من الخادم خطوة لاحقة تمسّ تحميل التطبيق كله.

**أ. إصلاح التصنيف ✅ منجز**

**من ٦٣١ تسمية إلى ٣٠ مهارة.** معدّل الأسئلة لكل مهارة: **٢٫٤ ← ٥٠**. الأدنى ٢٦، الأعلى ٨٥،
ولا سؤال واحد بلا تعيين.

`server/taxonomy.js` قائمة **مغلقة**، وقواعد تعيين مرتّبة لكل تصنيف. التسمية القديمة محفوظة
في عمود `skill` كمعلومة تحريرية؛ و`skill_id` هو وحدة القياس.

**حدّ الـ٢٥ مفروض باختبار** لا بنيّة: إضافة مهارة أدقّ بلا أسئلة تكفيها **تُفشِل البناء**.
هذا ما يمنع عودة المشكلة.

**قرارا تصميم:**

1. **مهارة واحدة قد تشمل تصنيفين** حين يكون المفهوم واحدًا. حساب المتوسط مهارة واحدة سواء
   صنّف البنك السؤال تحت «الحساب» أو «الإحصاء». التصنيف يصف بنية الاختبار، والمهارة تصف
   الطالب — وأنا أقيس الطالب.
2. **رفضت تقسيمًا وهميًا.** كان لديّ `VO-CLASS` و`VO-TRAIT` في الارتباط والاختلاف، ثم تبيّن
   أن الفارق بينهما هو **ورود كلمة «تصنيف» في التسمية القديمة** لا ما يفعله الطالب. كل أسئلة
   الارتباط مهمة تصنيف واحدة. دمجتهما: تقسيم يعكس طريقة التوسيم لا المهارة هو ضجيج قياس.

**عيب التقطته في التدقيق:** عشرة أسئلة نسبة مئوية كانت تذهب إلى «خواص الأعداد»، لأن نمطي
`نسبة مئوي` لا يطابق `النسبة المئوية` (أداة التعريف والتاء). وسؤال `كلّ وبدايته` لم يُعيَّن
أصلًا لأن الشدّة تكسر المطابقة — فصار التجريد من التشكيل خطوة أولى في التعيين.

**ما لم أقسّمه، وهي فجوات محتوى معروفة** (`PENDING_SPLITS` في الشفرة): الطردي/العكسي،
الأسس/خواص الأعداد، الزوايا/فيثاغورس، التحليل/التبسيط، النزعة/التشتت، الاحتمال البسيط/العدّ،
التضاد/جزء وكل، المنطق/الحقيقة، الزوج/المفردة. كلها دون ٢٥ سؤالًا، والتقسيم **آلي** متى
وُجدت الأسئلة. الفرق بين الطردي والعكسي مهم تعليميًا (الطلاب يخلطونهما) ولا يمكن قياسه
بـ١٣ سؤالًا.

**الأدوات:** `node server/cli.js skills` يطبع التغطية ويعلّم ما دون ٢٥.
`backfill-skills` يملأ قواعد مهاجَرة قبل التصنيف. البوابة تعرض قائمة المهارات مرشّحة بالقسم
مع عدد الأسئلة المنشورة في كل مهارة، وتستنتج المهارة إن تُركت فارغة — فقالب Excel يعمل
بلا تغيير (لا عمود مهارة فيه).

**ب. كيان النص المستقل ✅ منجز**

**٥٦ نصًا تخدم ٢٥٤ سؤالًا** — كل نص يحمل ٣–٥ أسئلة، وهذا شكل الاختبار الحقيقي بالضبط.
البنية كانت منتظمة تمامًا (`النص: …` ثم سطر فارغ ثم السؤال في الـ٢٥٤ كلها)، فالفصل قاطع لا
تخميني.

| | قبل | بعد |
|---|---|---|
| نسخ النصوص | ٢٥٤ | **٥٦** |
| حجم نصوص الاستيعاب | ١٢٩٦٧٣ حرفًا | **٣٦٥٩٦** (‑٧٢٪) |
| تعديل نص واحد | ٥ تعديلات | **تعديل واحد** |

**الفصل بلا أي فقد:** الاختبار يعيد تركيب كل سؤال من نصه وجذعه ويقارنه بالأصل حرفًا بحرف —
٢٥٤ من ٢٥٤ متطابقة.

**ما اكتُشف أثناء العمل:**

1. **البصمة كانت ستصبح خطأً.** تقصير `text` إلى السؤال وحده يعني أن «ما الفكرة الرئيسة
   للنص؟» يصير جذعًا واحدًا عبر كل النصوص. لم يحدث تصادم في البنك الحالي، **لكن ذلك حظ لا
   ضمانة**. البصمة الآن تربط السؤال بنصّه، ومن لا نص له يُبصَم كما كان تمامًا فلا شيء آخر
   يحتاج إعادة حساب.
2. **`passage_id = ''` كسر مفتاح العلاقة.** السلسلة الفارغة ليست `NULL`، فبحثت القاعدة عن نص
   بمعرّف فارغ وفشلت الهجرة كلها. الآن `NULL` عند عدم وجود نص — وSQLite تتجاوز الفحص عليها.
3. **علة في الواجهة:** رسالة النجاح كانت تُكتب في عقدة ثم `render()` يعيد البناء فيمحوها، فلا
   يرى المدير تأكيدًا وإن نجحت العملية. الرسائل الآن في الحالة، تُعرض مع العرض.

**الضمانات:** تعديل النص يسري على كل أسئلته، ويُعيد المنشور منها إلى المراجعة (الطالب يقرؤه
الآن)، ويُعيد حساب بصماتها. ونص عليه أسئلة **لا يُحذف** — الخادم يرفض والواجهة لا تعرض الزر.

**البوابة:** تبويب «النصوص» يكتب النص مرة ويعرض أسئلته تحته. ونموذج الإدخال يُظهر قائمة
النصوص فقط عند تصنيف الاستيعاب. ومن يرسل الصيغة المدمجة (كما في Excel) يُفصل له تلقائيًا
ويُربط بالنص نفسه بلا نسخة ثانية — فالقالب يعمل بلا تغيير.

**الواجهة الآن تقرأ من الخادم ✅** (البند التالي).

**ج. تحويل الواجهة إلى الخادم ✅ منجز**

`GET /api/bank` يخدم الأسئلة **المنشورة فقط**، مبنيًّا من `items` و`passages`. ومُحمِّل
`dist/bank.js` يضعه في `window.GAT_BASE` قبل أن تقرأه أي وحدة — أُدخل في سلسلة التحميل بعد
`data.js` ويُنتظَر، فالبنك نهائي قبل `core.js`.

**ما يراه الطالب الآن:** البنك من قاعدة البيانات. أي سؤال تضيفه من البوابة وتنشره يصل إليه،
وأي تعديل على نص يصل إلى كل أسئلته. بلا إعادة تشغيل — الخادم يكتشف تغيّر القاعدة ببصمة منها.

**السقوط الآمن — ثلاث حالات مُختبَرة في متصفح حقيقي:**

| الحالة | السلوك |
|---|---|
| لا خادم / `file://` / استضافة ثابتة | النسخة المرفقة، كما كان تمامًا |
| جدول الأسئلة فارغ (لم تُشغَّل الهجرة) | ‎404 من الخادم، والنسخة المرفقة |
| حمولة ناقصة أو مشوّهة | **تُرفض**، والنسخة المرفقة تبقى |

المبدأ: **لا يُستبدل بنك عامل ببنك ناقص**. شاشة بلا أسئلة أسوأ من بنك الأمس.

**ما اكتُشف أثناء العمل:**

1. **ذاكرة مؤقتة خدمت ٤٠٤ بعد نجاح الهجرة.** خزّنت البنك الفارغ ثم لم يُبطَل، والهجرة من سطر
   الأوامر تكتب من **خارج** الخادم فلا تستطيع إبطال ذاكرته. صار مفتاح التخزين **بصمة من
   القاعدة** (عدد المنشور وآخر تحديث)، والبنك الفارغ لا يُخزَّن أصلًا.
2. **تأكيد فضفاض في اختباري.** فحصت أن جذع السؤال لا يحتوي «النص:» فأخفق على أربعة جذوع
   مشروعة تنتهي بـ«في النص:» قبل إجابتها. الفحص الصحيح: ألا **يبدأ** الجذع بالعلامة.

**الأداء:** الحمولة ٨٣٩ كيلوبايت (gzip يضغطها كثيرًا)، و٢٠ طلبًا من الذاكرة في ٢٨٧ مللي ثانية.
والنصوص تُرسل **مرة واحدة** في مصفوفة مستقلة، ويعيد المُحمِّل تركيبها للعروض التي تتوقّع نصًا
واحدًا، مع إبقاء `passageText` و`passageId` على السؤال لمن يعرضهما منفصلين.

**ما لم يتغيّر:** `qiyas.js` يفصل النص للعرض بالفعل عبر `.q-passage`، لكنه يعرضه **مع كل
سؤال**. عرض النص مرة واحدة فوق مجموعة أسئلته يحتاج تجميعًا في واجهة الامتحان — بند مستقل،
وأصبح ممكنًا الآن لتوفّر `passageId`.

**د. تجميع النص مع أسئلته ✅ منجز**

التجميع كان موجودًا (`passageKey` واختبار يؤكّد تجاور أسئلة النص)، لكن **الطالب لا يعرفه**:
النص يُعاد فوق كل سؤال بلا إشارة، فيُعيد قراءته أربع مرات. ما أُضيف:

- `passageKey` يعتمد `passageId` حين يأتي البنك من الخادم (والنص يبقى بديلًا للنسخة المرفقة).
- سطر فوق النص: **«نص جديد · ٤ أسئلة عليه»** ثم **«النص نفسه · السؤال ٢ من ٤ عليه»**.
- موضع تمرير النص محفوظ داخل المجموعة، فلا يُقذف الطالب إلى أعلى نصٍّ هو في وسطه.

كل ذلك في `enhanceQuestionText`، وهو **مُحسِّن لاحق** يعمل عبر `MutationObserver` — فلم يُلمس
منطق التنقّل الذي تغطّيه اختبارات الموثوقية. والاختبار **يقود الواجهة كما يفعل الطالب**
(يبدأ المحاكاة ويضغط «التالي») لأن كل وحدات التطبيق مغلّفة ولا تُستدعى من الخارج.

**هـ. دفعة ١٠٠ سؤال ✅ منجزة**

| | العدد |
|---|---|
| إجمالي | **١٠٠** |
| صعب | **٨٥** |
| متوسط | ١٥ |
| سهل | **٠** — البنك ٦٣٪ سهل أصلًا |
| نصوص جديدة | ٦، ثلاثة أسئلة لكل نص |

**وُجّهت للفجوات لا عشوائيًا.** خمس مهارات كانت **بلا سؤال صعب واحد** صار لكل منها ٥–٦:
`VC-CONTEXT`، `VO-CLASS`، `VR-MAIN`، `VR-MEANING`، `VR-DETAIL`. ولو نُشرت الدفعة يرتفع
الصعب من **١٤٧ إلى ٢٣٢ (+٥٨٪)**.

**المفاتيح محسوبة لا مفترضة.** كل سؤال كمّي يحمل تعبير `check` يُحسب في
`scripts/check-batch.cjs` ويجب أن يطابق الخيار الذي يشير إليه المفتاح — **٤٣ من ٤٣ محسوبة**،
والاختبار يزرع مفتاحًا خاطئًا ليثبت أن الفاحص يلتقطه.

**ثلاثة عيوب في تأليفي التقطها الفاحص:**

1. **نسيت حقل المرجع في الـ٤٣ كلها** فرفضها المُصادِق — قاعدة الأصالة تعمل.
2. **سؤال بخمسة خيارات** (خيار فارغ زائد).
3. **سؤال أرقامه لا تعطي ناتجًا نظيفًا**: ٤٢٤ ÷ ٠٫٨٨ = ٤٨١٫٨٢، فأُعيد بناؤه على ٤٤٠ ← ٥٠٠.

وعيب رابع في **فاحصي** لا في الأسئلة: `0.75 * 0.8` تساوي `0.6000000000000001` في الحاسوب،
فرفضت المقارنة الصارمة ستة مفاتيح صحيحة. أُضيفت دالة مقارنة بهامش.

**الدفعة مسوّدات، لا منشورة.** `author_kind = 'ai'` و`author_model = 'claude-opus-5'` على كل
سؤال، ولا يستطيع المستورد نشر شيء: **تحتاج مراجعتك من `items.html`** قبل أن يراها طالب. هذا
ما بنيته الضمانة من أجله، ولم أتجاوزه لأنني أنا المؤلّف.

**و. استيراد بترتيب أعمدة آخر ✅ منجز**

أُضيف نظام **أنماط أعمدة** يُكتشف من صف العناوين، لا قالب واحد مفروض. الفروق التي يتولّاها:
القسم بأداة التعريف (`الكمي` ← `كمي`)، و«الموضوع / المجال» الحر يُطابَق على قائمة التصنيفات
المغلقة، و**الإجابة المكتوبة كقيمة** تُطابَق على الخيارات، و«إستراتيجية الحل السريع» تُحفظ في
عمود مستقل عن الشرح.

**لا تخمين:** قيمة إجابة تطابق خيارين أو لا تطابق أيًّا منها تُرفض بسببها مذكورًا، والصفوف
المرفوضة تُكتب في تقرير `<الملف>-rejects.json`. وتطابق العناوين جزئيًا **لا يُعدّ تطابقًا** —
النمط الخاطئ يُزيح عمود الإجابة فتصير كل مفاتيح الملف على خيارات خاطئة.

**ما كشفه الملف الحقيقي (٥٠٠ صف):**

| | العدد |
|---|---|
| صفوف | ٥٠٠ |
| **أسئلة متمايزة صالحة** | **١٧٠** |
| نسخ مكرّرة حرفيًا | **٣١٢** |
| صفوف بخيارات مكرّرة | ١٨ (خمسة منها مفتاحها غير محدَّد) |

التكرار مركّز في اللفظي: ٦٦ نسخة فائضة في «المفردة الشاذة»، و٥٦ في «إكمال الجمل»، و٥٦ في
«الخطأ السياقي». وأكبر مجموعة **١٨ نسخة متطابقة** من سؤال واحد. والعيب الآخر ميكانيكي: مموّه
مكرر مثل `["26","31","25","31"]`، وحين يكون المكرر هو المفتاح يصير غير محدَّد.

**ز. دفعة ١٠٠ سؤال ثانية ✅ منجزة**

١٠٠ سؤال (٨٥ صعب، ١٥ متوسط، صفر سهل)، موجّهة لما بقي رقيقًا بعد الدفعة الأولى: ٦٦ كمّيًا
بمفاتيح محسوبة، و٢٢ لفظيًا، و١٢ استيعابًا على أربعة نصوص جديدة. والحرس رفض سؤالًا واحدًا
لتطابقه مع `Q-A-021` في البنك، فاستُبدل.

**الحصيلة بعد الدفعتين:** ٢٠٠ مسوّدة، ٦٦ نصًا، والصعب **١٤٧ ← ٣٢٠ (+١١٨٪)** لو نُشرت. ومتوسط
الصعب لكل مهارة ١١، وأدناها ٦.

**ح. دفعة ثالثة + أداة فحص جماعي + تعليمات للمولِّد ✅ منجزة**

**`docs/GENERATOR_BRIEF.md`** — ملف جاهز للإرسال لأداة التوليد، مبنيّ على قياس فعلي للجزء
الأول لا على تقدير: العيوب الثلاثة ومنطق البصمة المطلوب نسخه، وعقد الأعمدة، والمواضيع
المقبولة، وتوزيع صعوبة مطلوب (٥٠٪ صعب)، ومعيار قبول قابل للتحقّق.

**`audit-xlsx`** — أمر **لا يكتب شيئًا**، يفحص الملفات العشرين مجتمعة ويقيس ما لا يظهر في ملف
واحد: **التكرار بين الملفات**. تجربته على نسختين من الجزء الأول أعطت ١٧٪ حصيلة كلية (١٧٠
سؤالًا جديدًا من ١٠٠٠ صف).

**الدفعة الثالثة:** ١٠٠ سؤال **كلها صعبة**، ٤٤ كمّيًا بمفاتيح محسوبة و٥٦ لفظيًا مع أربعة نصوص
جديدة.

**الفاحص التقط خمسة أخطاء في تأليفي، منها اثنان مفتاحان خاطئان فعلًا:**

| | الخطأ | التصحيح |

| ٢٢ | زمن الدراج: المفتاح على ١٥ والحساب ٢٤ | صُحّح المفتاح وأُعيد بناء الشرح |

واستبدلت سؤالًا سادسًا بنفسي: زوج تناظر علاقته غير بيّنة وشرحي فيه مضطرب يناقض نفسه.
**الفاحص لا يلتقط شرحًا مضطربًا — هذا ما يبقى على المؤلّف.**

**الحصيلة بعد ثلاث دفعات:**

`server/calibration.js` يحسب لكل سؤال `p_value` و`r_pbis` وأنصبة المموّهات، ويرفع أعلام الجودة.

**قرار إحصائي جوهري:** `r_pbis` **مُصحَّح** — درجة المقارنة لكل طالب تستثني السؤال المعاير.
بلا ذلك يرتبط السؤال جزئيًا بنفسه فيتضخّم الرقم لكل الأسئلة، وأكثر ما يتضخّم في الاختبارات
القصيرة. التصحيح ليس تحسينًا، بل هو ما يجعل الرقم يعني ما يُدّعى له.

**الاختبار يقيس الاسترجاع لا التشغيل.** يولّد أسئلة بمعاملات (تمييز وصعوبة) **لا يعرفها الخط**،
ثم يتأكد أنه يسترجعها:

| التمييز a | ٠٫٣ | ٠٫٨ | ١٫٥ | ٢٫٥ |
|---|---|---|---|---|
| `r_pbis` المرصود | ٠٫١٢ | ٠٫٢٧ | ٠٫٤٢ | **٠٫٤٩** |

و`p_value` ينقص مع ارتفاع الصعوبة عند كل مستوى تمييز. ويُختبر أيضًا أن **مفتاحًا خاطئًا يظهر
كارتباط سالب** — وهو أهم ما تكشفه المعايرة عمليًا.

**العزل بنيوي لا اتفاقي.** بدأت بعمود `synthetic` على جدول الإجابات، ثم بدّلته: العمود يبعد
شرطًا واحدًا منسيًّا عن تقديم بيانات مصنوعة كأنها دليل. الآن **جدول `synthetic_responses`
مستقل**، و`item_stats` مفتاحه `(item_id, synthetic)`. ولا مفتاح علاقة إلى `users` — فالمُحاكى
ليس حسابًا، ولا يستطيع المُحاكي لمس صف طالب حقيقي. (كشف ذلك فشلُ مفتاح علاقة عند أول تشغيل.)

**ما لم أفعله:** لم أكتب إجابة اصطناعية واحدة في قاعدة إنتاج. أرقام المعايرة الحقيقية **فارغة**
وتبقى كذلك حتى يجيب طلاب. و`calibrate` بلا `--synthetic` يقول صراحة: «لا توجد إجابات في هذه
المجموعة بعد».

**د. معايرة تجريبية** — بعد ~٣٠٠ إجابة لكل سؤال من `responses`:
- `p_value` = نسبة الإجابة الصحيحة (الصعوبة الحقيقية)
- `point_biserial` = ارتباط السؤال بالدرجة الكلية (قوة التمييز)
- تحليل المموّهات: خيار لا يختاره أحد = سؤال من ٣ خيارات فعليًا
- **بوابة جودة:** كل سؤال بـ `point_biserial < 0.15` أو `p_value > 0.95` أو `< 0.15` يُعلَّم للمراجعة تلقائيًا

**معيار الإنجاز:** ≥٢٥ سؤالًا لكل `skill_id`، صفر نص مكرر، تقرير معايرة أول يصنّف البنك إلى محتفظ/مراجَع/مسحوب.

### المرحلة ٢ — التعلّم الذكي (٤–٥ أسابيع)

هنا يتحوّل المنتج من "بنك أسئلة" إلى "منصة".

- **تشخيص قصير**: ٣٠–٤٠ سؤالًا تختار العنصر التالي حسب الأداء (تكيّف بسيط قائم على الصعوبة المعايرة، لا IRT كامل بعد) → تقدير أولي لكل مهارة
- **نموذج إتقان لكل مهارة**: بايزي بسيط (معرفة سابقة + تحديث بعد كل إجابة)، يميّز "لم يتدرّب" من "تدرّب وأخفق"
- **الجلسة اليومية المركّبة**: ٦٠٪ مراجعة متباعدة مستحقّة + ٣٠٪ أضعف مهارة + ١٠٪ سؤال أصعب بدرجة من مستواه الحالي
- **التدخّل عند الخطأ**: الشرح موجود في البنك، لكن الشرح وحده لا يعلّم. أضف: سؤالًا موازيًا فوريًا لنفس المهارة بأرقام مختلفة
- **تحليل الوقت**: `ms_spent` يميّز "لا يعرف" (سريع وخاطئ) من "يعرف ولا يُنجز" (بطيء وصحيح) — واستراتيجية العلاج تختلف جذريًا

**مبدأ تعليمي أرفض التهاون فيه:** لا تعرض للطالب "درجة قياس المتوقّعة" رقميًا. البنك غير معاير على عيّنة تمثيلية، وأي رقم سيكون وعدًا لا تستطيع الوفاء به — وهو أسرع طريق لفقدان الثقة ولمشكلة قانونية. اعرض **نطاق إتقان لكل مهارة** و**اتجاه التحسّن**. الواجهة الحالية تلتزم بهذا بالفعل (`learn.js`: «لا تعرض المنصة درجة معيارية أو توقعًا لدرجة قياس») — أبقِ الالتزام.

**معيار الإنجاز:** طالب يكمل التشخيص ثم ٧ جلسات يومية، ويظهر تحسّن قابل للقياس في المهارات المستهدفة مقابل مجموعة ضابطة تتدرّب عشوائيًا.

### المرحلة ٣ — تجربة الطالب والاحتفاظ (٣ أسابيع) ← بديل مسار المؤسسات

بعد حصر النطاق على الطلاب، هذه المرحلة هي ما يحمي الإيراد: الاحتفاظ.

- **بوابة إدخال الأسئلة الموحّدة**: المسارات الثلاثة (يدوي / Excel / عند الإنتاج) في مُخطَّط
  واحد وحالة `draft → reviewed → live`
- **تقرير محاكاة مفصّل**: الأداء بالقسم وبالمهارة، منحنى الوقت، الأسئلة المتروكة، ومقارنة
  بالمحاكاة السابقة
- **سلسلة الأيام وأهداف أسبوعية** — أبسط رافعة احتفاظ وأرخصها
- **تنبيه بالبريد**: «لم تتدرّب ٣ أيام»، وتقرير أسبوعي. يحتاج التحقّق من البريد (المرحلة ١)
- **ولي الأمر كمُشاهد فقط**: رابط تقرير للقراءة، بلا حساب — هو من يدفع غالبًا، ورؤيته
  للتقدّم ترفع التجديد. أقل جهد بأعلى أثر على الإيراد
- **محاكاة كاملة بالمؤقّت على الجوّال** — تُختبر فعليًا على جهاز حقيقي

**معيار الإنجاز:** ≥٤٠٪ من المشتركين يكملون محاكاتين أو أكثر، و≥٢٥٪ يعودون في الأسبوع ٤.

### المرحلة ٤ — التجاري (٣ أسابيع، بالتوازي مع ٣)

- اشتراكات: مجاني + مشترك شهري + **باقة الدورة** (حتى موعد اختبارك) — الأخيرة تناسب الموسمية وسلوك الشراء
- بوابة دفع سعودية: **mada + Apple Pay إلزامي** — بلا mada لا سوق سعودي. (Moyasar / Tap / HyperPay — **[قرار مطلوب]**)
- فاتورة ضريبية متوافقة مع **ZATCA** (فاتورة إلكترونية، ١٥٪ ضريبة) — متطلّب نظامي لا اختياري
- حدود الخطة المجانية: ٣٠ سؤالًا/يوم، محاكاة كاملة واحدة
- لوحة مقاييس: التنشيط، الاحتفاظ بالأسبوع ٤، التحويل، الإيراد المتكرر

### المرحلة ٥ — الوصول والجوّال (مستمر)

- **PWA للعمل دون اتصال** — أولوية مرتفعة في السوق المستهدف، والأساس موجود (التطبيق ثابت أصلًا)
- إمكانية الوصول: قارئ الشاشة، تكبير الخط (موجود)، تباين، لوحة مفاتيح كاملة
- تطبيق أصلي: **[قرار مطلوب]** — PWA جيدة تكفي حتى الطلب الحقيقي؛ لا تبنِ تطبيقين قبل إثبات الاحتفاظ

## ٤. الاستراتيجية التجارية

### السوق

المتقدّمون لاختبار القدرات في السعودية **مئات الآلاف سنويًا**، والقرار الشرائي مدفوع بوالد قلق لا بالطالب — وهذا يغيّر كل شيء في التسويق والتسعير. السوق قائم اليوم على مراكز تدريب حضورية باهظة ومجموعات تلغرام مجانية رديئة. **الفراغ في المنتصف.**

### الشريحة الواحدة

**الطالب المتقدّم لاختبار قياس، والدافع غالبًا وليّ أمره.** القرار الشرائي عاطفي مدفوع بقلق
على مستقبل، لا بمقارنة ميزات — وهذا يحكم التسويق (الطمأنينة والوضوح، لا قوائم الميزات)
والتسعير (سعر دورة واحدة، لا اشتراك مفتوح بلا نهاية).

| الطبقة | المحتوى | الغرض |
|---|---|---|
| **مجاني** | تدريب سخي + محاكاة كاملة واحدة | **يعاير البنك** وهو جوهر قيمتك، ويثبت الجدية |
| **مشترك** | محاكاة غير محدودة + تقرير مفصّل + خطة مبنية على أدائه | الإيراد |

**لماذا الطبقة المجانية سخيّة؟** لأن كل إجابة مجانية تنتج بيانات معايرة. بلا مسار مؤسسي
يأتي بمئات الطلاب دفعة واحدة، الطبقة المجانية هي مصدر المعايرة الوحيد. اعتبرها استثمارًا في
الأصل، لا تكلفة اكتساب.

### الخندق التنافسي

الأسئلة ليست خندقًا. الخندق أربعة:

1. **بنك معاير تجريبيًا** — صعوبة حقيقية وتمييز مقاس، لا تخمين
2. **التكيّف المبني على تلك المعايرة** — يتحسّن مع كل طالب
3. **تاريخ الطالب داخل المنصة** — خطته وأخطاؤه ومنحنى تقدّمه؛ الانتقال يعني البدء من الصفر
4. **الالتزام التحريري الموثّق** — ١٠ دفعات مراجعة منشورة. الشفافية تبيع في سوق مليء بالوعود الزائفة

### المقاييس التي تحكم القرار

| المقياس | الحد المقبول |
|---|---|
| إكمال التشخيص | ≥٧٠٪ |
| العودة في الأسبوع ٢ | ≥٤٠٪ |
| العودة في الأسبوع ٤ | ≥٢٥٪ |
| التحويل من مجاني إلى مدفوع | ≥٥٪ |
| تجديد الاشتراك الفردي | ≥٣٥٪ |
| تحسّن مقاس على نموذج ثابت | ≥٨ نقاط مئوية بعد ٦ أسابيع |

الأخير هو المقياس الوحيد الذي يثبت أن المنصة **تعلّم**. البقية تثبت أنها تُستخدم. لا تخلط بينهما.

### المخاطر

| الخطر | الاحتمال | الاستجابة |
|---|---|---|
| **قانوني/حقوق** — مصادر مثل «تسريبات» | **مرتفع** | كل سؤال في البنك يجب أن يكون **مؤلَّفًا أصليًا**. راجع البنك لأي صياغة منقولة حرفيًا، ووثّق أصالة كل سؤال. هذا أخطر بند في الوثيقة. |
| استخدام علامة «قياس» أو «قدرات» بما يوحي باعتماد رسمي | مرتفع | إخلاء مسؤولية صريح في كل صفحة (موجود في الواجهة — أبقِه)، ولا تلميح لاعتماد |
| وعد بدرجة متوقّعة | مرتفع | ممنوع كما في المرحلة ٢ |
| الموسمية الحادة حول موعد الاختبار | مؤكد | **لا مكبح الآن** بعد إسقاط العقود السنوية: سعّر باقة الدورة الواحدة لتغطي الموسم، وخطّط التكاليف على قمة الطلب لا على متوسطه |
| منافس بتمويل أكبر | متوسط | المعايرة وجودة التقرير، لا عدد الأسئلة |

## ٥. الترتيب التنفيذي

```
المرحلة ٠  ▓                     أسبوع ١        أمان + CI + جدول responses
المرحلة ١  ░▓▓▓▓                 أسابيع ٢–٥     تصنيف + نصوص + بنك + معايرة
المرحلة ٢  ░░░░▓▓▓▓▓             أسابيع ٥–٩     تشخيص + إتقان + تكيّف
المرحلة ٣  ░░░░░░░▓▓▓▓           أسابيع ٨–١١    بوابة إدخال + تقرير محاكاة + احتفاظ
المرحلة ٤  ░░░░░░░░░▓▓▓          أسابيع ١٠–١٢   اشتراكات + mada + ZATCA
المرحلة ٥  ░░░░░░░░░░▓▓▓▓▓▓      أسبوع ١١+      PWA + وصول + جوّال
```

**المسار الحرج:** `responses` ✅ → معايرة → تكيّف → تقرير محاكاة مقنع → اشتراك. كل حلقة تعتمد على ما قبلها فعليًا، لا تنظيميًا.

**التالي:** المرحلة ١ — إصلاح تصنيف المهارات، وفصل النصوص، وبوابة إدخال الأسئلة. أكبر بند جهد في الخطة كلها هو تأليف ١٥٠٠ سؤال جديد.
